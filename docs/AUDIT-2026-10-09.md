# Audit technique — 9 octobre 2026

## Conclusion

Le prototype possède une base simple et compréhensible : six jeux, un service métier partagé entre HTTP et MCP, SQLite, des aperçus parent et un cache audio. Il présentait toutefois des défauts réels de contrôle serveur et de reprise réseau. Les corrections ci-dessous sont appliquées et vérifiées.

Le résultat est un prototype renforcé pour poursuivre le développement. Il n'est pas encore prêt pour l'accueil de vraies familles, de professionnels ou de milliers d'utilisateurs. Cet audit ne peut pas garantir l'absence de bugs et ne remplace pas un test de charge, un audit indépendant ou une revue du déploiement final.

Priorité confirmée : logopèdes et professionnels du soin avant enseignants et écoles. Voir [l'architecture cible](ARCHITECTURE.md).

## Périmètre inspecté

Code serveur et navigateur, schémas d'exercices, six jeux, profils, permissions, publication, API, SQLite/migrations, cache et coûts audio, scripts Windows, connecteurs locaux/distants, tests, dépendances, documentation et exploitation locale. Les secrets n'ont pas été exportés. Tests exécutés sur des données fictives isolées ; aucune synthèse ElevenLabs payante pendant la validation.

## Défauts corrigés

| Priorité | Constat initial | Correction et preuve |
|---|---|---|
| Haute | Un code de six lettres était aussi cherché parmi les prénoms ; `ARTHUR` pouvait donner accès au profil. | Recherche d'authentification strictement par code ; test métier et HTTP de refus du prénom. |
| Haute | Une requête pouvait terminer une quête sans jouer. | Le serveur vérifie chaque question ; refus HTTP 409 d'une fin prématurée. |
| Haute | Des réponses répétées produisaient des étoiles supplémentaires. | Question terminale verrouillée, comptage distinct, identifiant de requête persistant ; test de deux requêtes HTTP simultanées. |
| Haute | La fin de quête et le niveau étaient deux écritures séparées. | Transaction atomique ; une panne simulée entre les écritures annule l'ensemble. |
| Haute | La correction était renvoyée dès le premier essai incorrect. | Correction après réussite ou deuxième essai ; un retry du premier essai reste sans correction. |
| Haute | Le connecteur local publiait directement, sur la seule foi de sa description. | MCP local et distant préparent tous deux un brouillon à valider sur le Web. |
| Haute | Toute nouvelle phrase pouvait lancer une dépense audio, sans plafond durable ni délai réseau. | Génération désactivée par défaut, plafond quotidien SQLite avant chaque tentative, délai réseau, attente bornée, mode partagé toujours sans génération. |
| Moyenne | `.env` était chargé après des imports ouvrant déjà base et cache. | Configuration chargée par les modules qui dépendent des chemins ; erreur de lecture autre qu'un fichier absent signalée. |
| Moyenne | Schéma SQLite dispersé et migrations non versionnées. | Migrations sérialisées et versionnées, vérification des clés étrangères, index des relations ; tests sur base historique remplie et migrations répétées. |
| Moyenne | Les types étaient retirés par Node, mais jamais vérifiés. | TypeScript strict et commande `npm run verify` ; serveur et scripts contrôlés. Le navigateur JS n'est pas encore entièrement typé. |
| Moyenne | Entrées invalides transformées en chaînes, JSON malformé donnant des erreurs internes. | Schémas d'entrée, identifiants bornés, codes HTTP 400/413/415/429, limite réelle en octets UTF-8. |
| Moyenne | Aucune limite d'essais de codes ou de demandes. | Limites en mémoire par client/compte, taille maximale des compteurs et délais HTTP. Elles restent locales à un processus. |
| Moyenne | Protection de fichiers par simple préfixe de chemin. | Chemin décodé et normalisé, frontière de répertoire ; test de traversée Windows encodée. |
| Moyenne | Les tentatives disparaissaient de l'interface au rechargement. | État renvoyé par le serveur ; scénario navigateur avec rechargement après premier essai. |
| Moyenne | Une erreur réseau laissait les contrôles désactivés. | Contrôles réactivés, message doux et bouton Réessayer ; test navigateur avec arrêt/redémarrage du serveur de test. |
| Moyenne | Arrêt Windows fondé seulement sur le port. | Le script vérifie désormais le chemin du serveur ; le lanceur utilise un chemin absolu. Un ancien lancement non identifiable est refusé. |
| Moyenne | Pas de procédure de sauvegarde vérifiable. | `npm run backup` crée une copie cohérente et vérifie son intégrité ; test de restauration depuis une base WAL ouverte. |
| Faible | Dates dépendantes du fuseau du serveur. | Fuseau explicite Europe/Brussels, configurable ; retrait de jours calculé sur la date civile. |
| Faible | Cache audio navigateur et attente serveur sans borne. | Limite du cache navigateur, libération des URL audio, attente de synthèse plafonnée. |

## Risques encore ouverts

| Priorité | Risque | Étape de résolution |
|---|---|---|
| Bloquant pour familles réelles | Code enfant court et persistant, sans vraie session ; clé parent manuelle ; lien privé de brouillon transférable. | Comptes adultes, sessions enfant, expiration/révocation et validation parent liée à une identité. |
| Bloquant pour professionnels | Pas de consentement applicatif, invitation, partage limité, organisation ou journal d'accès. | Modèle familles/organisations/autorisations défini dans ARCHITECTURE.md, puis tests d'accès croisés et de révocation. |
| Bloquant pour commercialisation | Suppression/export/rétention, droits audio et cadre d'utilisation non finalisés. | Définir les politiques, les implémenter et les vérifier dans le contexte réel de déploiement. |
| Haute | Le endpoint voix accepte encore du texte arbitraire authentifié par code enfant. | Référencer uniquement des textes autorisés ; génération adulte/admin ; cache privé par famille. Le plafond actuel limite les dégâts sans remplacer ce contrôle. |
| Haute | Tutoriel/protection locale ne prouvent pas que l'humain a personnellement validé. | Validation Web authentifiée avec traçabilité ; aucun outil MCP pour auto-approuver. |
| Haute | Récompenses fondées sur compteurs et réponses ; suppression d'un exercice peut modifier les étoiles. | Registre d'attributions, inventaire serveur et politique d'archivage avant les nouveaux achats/cadeaux personnalisés. |
| Haute | Photos et extraits non vérifiés automatiquement ; question dépendant d'un support absent possible. | Contrat de support pédagogique et aperçu avec le même contexte que celui de l'enfant. |
| Moyenne | Brouillons expirés et journal audio continuent à occuper de l'espace. | Rétention bornée, purge contrôlée et supervision disque ; définir les durées avant toute suppression automatique. |
| Moyenne | Singleton SQLite, logique et SQL encore mêlés ; frontend de plus de 1 400 lignes. | Extraction progressive par domaine pendant les prochains chantiers, avec les tests de comportement comme garde-fous. |
| Moyenne | Séparateurs texte pour ordre/associations. | Remplacement futur par réponses structurées JSON avec migration/version de contrat. Les fragments contenant les séparateurs sont refusés en attendant. |
| Moyenne | CSP enfant complète, consentement à la voix distante et polices externes non traités. | Ressources locales, scripts d'essai séparés, politique de sécurité adaptée ; éviter toute affirmation de fonctionnement entièrement hors ligne. |
| Moyenne | Accessibilité incomplète : objets SVG et modales à revoir au clavier/lecteur d'écran. | Intégrer aux tests du nouvel espace personnel ; ne pas limiter la validation aux captures visuelles. |
| Moyenne | Certains changements rapides d'écran ou deux appareils peuvent produire des conflits d'interface. | Version d'état, annulation des opérations d'écran et tests multi-appareils. L'idempotence serveur protège déjà les écritures répétées. |
| Moyenne | Tunnel temporaire, PC nécessaire, absence de surveillance et sauvegarde hors machine. | Hébergement stable et procédure d'exploitation avant pilote. Le lien temporaire précédent était inactif à la vérification. |
| Moyenne | Aucun test représentatif de 1 000 utilisateurs ni validation multi-instance. | Scénario de charge avec métriques, seuils de latence/erreur et mesures de contention ; choix de base/hébergement ensuite. |
| Moyenne | Contrôles automatisés disponibles localement, pas encore exécutés par une plateforme CI distante. | Brancher `npm ci && npm run verify` à l'hébergement Git choisi avant le travail en équipe. |

## Vérifications exécutées

- `npm run verify` : contrôle TypeScript strict, formatage Prettier, syntaxe du navigateur et cinq suites de tests.
- Métier : six jeux, exercices invalides, accès croisés, premières/deuxièmes tentatives, idempotence, reprise, étoiles et transaction annulée lors d'une panne.
- MCP local : création de profil, brouillon invisible avant validation, contrat 5–8 questions, publication parent et progression.
- MCP distant : authentification/origine, isolation de deux familles, validation répétée, expiration, transport stdio, JSON invalide, dépassement UTF-8, traversée de chemin, limitation des essais et réponse concurrente.
- Audio simulé : cache, déduplication, changement de modèle, erreurs, mode partagé, activation explicite, budget et absence de texte dans les traces.
- Sauvegarde/restauration : copie d'une base WAL ouverte, contrôle d'intégrité, migration de la copie restaurée et égalité des profils.
- Windows : démarrage 2,21 s, réutilisation 0,48 s lors du contrôle ; un seul processus, page voix accessible, aucun appel externe.
- Navigateur : premier essai, rechargement, aide au deuxième essai, interruption de connexion, reprise, fin de mission. Formats téléphone et tablette vérifiés séparément.
- `npm audit --omit=dev` : zéro vulnérabilité signalée au moment du contrôle. Cela ne prouve pas l'absence de vulnérabilité applicative ou non référencée.
- Dépôt Git local initialisé : code, tests et décisions peuvent maintenant être versionnés. Données, clés et réglages locaux sont exclus ; aucun dépôt distant créé ni code envoyé.

## Ordre des prochains travaux

1. Nouvelle récompense et espace personnel : registre d'attribution + inventaire persisté avant l'interface de personnalisation ; goûts et niveau de lecture indépendants de l'âge.
2. Comptes, familles, sessions et espace parent ; migration des profils de prototype sans considérer le code enfant comme identité adulte.
3. Invitations de professionnels du soin avec portée limitée, échéance, révocation et historique ; tests de chaque permission.
4. Hébergement, sauvegardes externes, suivi d'erreurs/performances, rétention/export/suppression et test de charge pour un pilote limité.
5. Offres gratuites/payantes et quotas ; enseignants/écoles ensuite selon le même modèle d'organisation.

Les étapes peuvent être préparées en parallèle sur le plan de la conception ; l'ouverture publique dépend des points bloquants, pas de la richesse des animations.
